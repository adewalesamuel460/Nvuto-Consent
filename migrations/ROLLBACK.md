# Migration rollback strategy

`002_policy_governance.sql` is additive except for widening the existing consent-status constraint. The previous API can continue reading and writing legacy columns after the migration, so the safe rollback is an application rollback to the prior image while retaining the added schema and evidence. This preserves receipts, notices, audit records, and pending outbox events.

Do not drop the added tables or columns during an incident rollback. Doing so would destroy compliance evidence and can strand `pending_confirmation` records. If a schema defect is discovered, pause registry writes and outbox publication, take a verified PostgreSQL backup, deploy a forward corrective migration, validate row counts and constraint state, then resume workers. Destructive schema removal is a separately reviewed data-retention operation, not an automated rollback.

`004_preference_generation_receipt_v2.sql` is additive (`consent_preference_state`, `consents.preference_generation`, `consent_receipts.hash_version`). Rolling the application back to a pre-004 image is schema-safe but re-opens T-001: the old image ignores generations and confirms by token alone. Prefer a forward fix. If a rollback is unavoidable, keep the schema, and record the rollback window. Rows the old image writes carry `preference_generation = 0`, and the new image ranks effective state by generation before `updated_at`, so before rolling forward again either re-express every preference written during the window through the new image or run a reviewed corrective migration that assigns those rows generations above the current `consent_preference_state.generation`. Otherwise a denial or withdrawal written during the window can be outranked by an older grant. Generation-0 pending challenges are always treated as stale and must be re-issued. Receipts with `hash_version = 2` remain verifiable only by the new verifier; never rewrite `receipt_hash` or `hash_version` on existing rows.

`005_outbox_fencing.sql` is additive (`consent_outbox_events.claim_token` plus the `consent_outbox_fence_untokened_writes` trigger). Apply it before rolling out the fenced worker image. While old and new workers coexist, the trigger fences pre-005 workers. They can still claim expired rows: an old-style claim sets a new `locked_at`, and the trigger clears the token, which revokes the newer lease. They can also complete rows that they own. But an old worker cannot publish-mark, reschedule or unlock a row that holds a live claim token, and gets SQLSTATE 55000 instead. Rolling the worker image back is therefore schema-safe. Old workers log 55000 for token-owned rows until those leases (2 minutes) expire, then resume normally. Do not drop the trigger while any fenced worker is running. If 005 itself must be backed out, scale the workers to zero first, then drop the trigger in a reviewed forward migration. Keep the column.

`006_schema_hardening_and_audit.sql` is additive (`consents(tenant_id, id)` composite uniqueness, `consent_receipts` and `consent_idempotency` composite foreign keys, `consent_suppressions` scope shape CHECK constraint, `consent_audit_events` resource_type/revision/changes columns, and `consent_idempotency.response_snapshot` column). Rolling back application code to a pre-006 image is schema-safe: pre-006 binaries insert into the same tables and default columns safely. Do not drop foreign keys, constraints or added columns during an incident; keep the schema and roll forward if fixes are required.

`007_protected_suppressions.sql` is additive (`consent_suppressions.created_by_role`). Rolling back application code to a pre-007 image is schema-safe: pre-007 binaries read and write `consent_suppressions` safely with the added column defaulting to `''`. Do not drop the column during an incident rollback; keep the column and roll forward if fixes are required.

`008_receipt_evidence_binding.sql` is additive (`consent_privacy_notices` content/content_hash/retired/superseded_by columns and `consent_receipts` actor_id/consent_status/legal_basis/notice_content_hash/policy_version columns, with triggers protecting notice and receipt immutability). Rolling back application code to a pre-008 image is schema-safe: older binaries continue to query and insert rows safely using default column values. Do not drop columns or triggers during an incident rollback; keep the schema and roll forward if fixes are required.

`009_legacy_quarantine_reconciliation.sql` is additive (`consent_legacy_reconciliation` audit table and `view_consent_legacy_classification` view). Rolling back application code to a pre-009 image is schema-safe: older binaries do not reference the reconciliation table or view. Do not drop the table or view during an incident rollback; retain reconciliation audit records and roll forward if fixes are required.

`009_audit_history_enhancement.sql` is additive (`consent_audit_events` columns: `resource_type`, `resource_id`, `revision`, `before_state`, `after_state`, `correlation_id`, `reason`, index `idx_consent_audit_export`, and the `trg_consent_audit_immutable` trigger enforcing strict append-only immutability against UPDATE and DELETE). Rolling back application binaries to a prior image is schema-safe: older binaries continue to insert rows using defaults and cannot mutate existing audit rows. Do not drop added audit columns or disable the immutability trigger during an incident rollback, as this would compromise the cryptographic and legal integrity of the compliance audit trail; prefer forward corrective fixes if necessary.

`010_idempotency_snapshots.sql` is additive (`consent_idempotency` columns: `request_hash`, `response_snapshot`, `original_response`, and the retention index `idx_consent_idempotency_retention`). It backfills between `original_response` and `response_snapshot` for historical rows. Rolling back application code to a pre-010 image is schema-safe: older binaries continue to query and insert into `consent_idempotency` using existing columns and defaults. Do not drop added columns or the retention index during an incident rollback; keep the schema and roll forward if fixes are required.
