# 06 — Backend and API audit

**Audit date:** 19 October 2026. **Scope:** the supplied NVUTO Consent API, domain/service/repository wiring and outbox interfaces. **Assessment:** all eleven documented business operations are registered, but production acceptance fails on consent ordering, double-opt-in authorization/proof, receipt integrity and other confirmed defects. Runtime evidence covers local unit/handler tests and narrowly scoped audit probes; durable HTTP/YSQL and external consumer flows remain unverified.

The original suite produced **15 PASS / 3 SKIP**, also under race detection. Separate audit probes produced **11 FAIL + 1 OBSERVATION** against unchanged implementation in a disposable copy. A failed probe is a reproduced counterexample to its safety assertion, not a failed implementation attempt. Detailed commands, environment and test limits are in [14_TESTING_QA_AND_VERIFICATION_REPORT.md](14_TESTING_QA_AND_VERIFICATION_REPORT.md) and [21_AUDIT_EVIDENCE_AND_COMMAND_LOG.md](21_AUDIT_EVIDENCE_AND_COMMAND_LOG.md).

Source references are relative to the repository root. Canonical F/T/AT/G identifiers refer to [findings](15_PRODUCTION_BLOCKERS_AND_RISK_REGISTER.md), [implementation tickets](16_DETAILED_IMPLEMENTATION_BACKLOG.md), [acceptance cases](14_TESTING_QA_AND_VERIFICATION_REPORT.md) and [release gates](19_PRODUCTION_GO_LIVE_CHECKLIST.md). No implementation was changed during this audit.

## 1. Backend architecture and active execution paths

The repository is one Go module with two deployable processes. Go `net/http` handlers invoke a service with a repository interface; the production implementation uses pgx against YugabyteDB YSQL. The separately running outbox worker reads durable events and publishes to NATS JetStream. It is not a full frontend/backend monorepo. The production datastore intent is explicit in `README.md:45-51`; the `Postgres` type name and PostgreSQL-compatible driver do not change that intent.

The production write paths use repository transactions to group business changes with receipts where applicable, audit rows and outbox records. That is a source property requiring durable verification; it is not proof that a target YSQL deployment survives node loss or every transaction fault. F-016/[AT-016](14_TESTING_QA_AND_VERIFICATION_REPORT.md#at-016) defines the missing evidence.

Separately, migration-retained blank-notice records skip policy checks during evaluation, F-008.

## 2. Shared HTTP contract and runtime behavior

Every business route applies its method guard before authentication (`cmd/server/main.go:101-107` and handlers). All handler-produced responses set `Content-Type: application/json` and encode a JSON value with newline (`59-63`). Every JSON-consuming handler uses one decode against `http.MaxBytesReader` set to 1 MiB and rejects unknown fields (`78-85`). It does **not** require a JSON `Content-Type`, check for EOF after the first JSON value, reject duplicate object keys or provide field-specific validation messages. A request containing one valid object followed by another object can be accepted; see [F-027](15_PRODUCTION_BLOCKERS_AND_RISK_REGISTER.md#f-027) and temporary audit probe. Over-limit and parse/type/time-format errors map to generic 400 `{"error":"invalid json"}` rather than distinct 413/415 results.

Authentication failures are 401 with a variable error string; role failures 403 `role not authorized`; subject failures 403 `subject not authorized`; wrong method 405 `method not allowed` with no `Allow` header; store not found 404 `not found`; unique/store conflict 409 `conflict`; expired confirmation 410 `expired`; **all other service/store/runtime errors** 422 with raw `err.Error()` (`cmd/server/main.go:65-75`, `88-106`). Unknown paths handled by the standard mux may return its default non-JSON 404/redirect behavior, unlike errors written by a known handler. No machine-readable error code, request/correlation ID, trace ID, retry hint or idempotency replay indicator is included.

There is no API request-rate limiter, per-tenant quota, CORS policy, OPTIONS preflight handler, CSRF/session-cookie implementation, API gateway implementation, API version negotiation, pagination helper, filtering helper or structured access logging in this server. Missing CORS is a conditional browser-integration issue: a same-origin gateway can satisfy browser needs; a cross-origin portal requires a defined CORS contract. Do not infer that a gateway already supplies it. No route here accepts a cookie-based session; authentication is the external bearer JWT or explicit dev modes.

API listens on `:8080` with ReadHeaderTimeout 5 s; ReadTimeout 15 s; WriteTimeout 15 s; IdleTimeout 60 s; shutdown budget 15 s (`cmd/server/main.go:435`, `452-455`). Production store bootstrap pings the configured database (`417-430`; `internal/store/postgres.go:17-34`). TLS termination is not implemented in this `ListenAndServe` entry point (`439`). Authentication is evaluated per request rather than validated during `main`; readiness calls only repository Ping (`392-397`; `internal/service/service.go:390`). F-015 and the deployment/security reports cover the resulting readiness gates.

## 4. Request and response schema detail

### 4.1 Direct consent body — active API-04

Accepted JSON properties are exactly `subject_id:string`, `purpose:string`, `channel:string`, `legal_basis:string`, `status:string`, `source:string`, `scope:object<string,string>`, `expires_at:RFC3339 time or null`, `jurisdiction:string`, `notice_version:string`, `evidence:Evidence` (`cmd/server/main.go:23-35`). Tenant, actor, consent ID, receipt ID, version and creation timestamps cannot be supplied in this request type; unknown fields cause400. `status` normalizes to only granted or denied. `subject_id` is trimmed, purpose/channel/legal_basis/status/source lowercased and trimmed, jurisdiction uppercased and trimmed, notice_version trimmed (`internal/service/service.go:121-139`). Self-service subject comparison occurs **before** normalization (`cmd/server/main.go:192`), so whitespace around an otherwise matching subject can produce 403 while a privileged call trims it.

Direct grants and denials both require an active purpose containing the channel, active lawful basis whose categories include the purpose category, and active notice in the jurisdiction/version that is already published. If that basis requires evidence, evidence.method and evidence.artifact_hash must be nonempty and collected_at must be >=notice.PublishedAt and <=server now (`internal/service/service.go:88-105`). The hash text is not checked for algorithm, length, hex format or linkage to notice content. A denied preference is subject to the same policy/evidence checks. `expires_at` is not checked for being future, after collection, or after grant; past dates can produce a newly created granted record immediately evaluated as expired (`internal/service/service.go:138-139,367-368`). `scope` is stored metadata; the evaluator has no scope input and does not inspect it. Numeric rates, field maximum lengths, key vocabularies and geographical legal rules are not defined at this layer.

### 4.2 DOI request — API-09

Properties exactly `subject_id`, `purpose`, `channel`, `source`, `jurisdiction`, `notice_version`, `evidence`, `expires_at` (`cmd/server/main.go:48-57`). There is no destination email address/phone, legal_basis override, consent-duration expiry, scope or caller callback URL. `expires_at` is the **confirmation challenge** expiry, not Consent.ExpiresAt, which remains nil (`internal/service/service.go:278-295`). No maximum challenge duration is imposed. Legal basis is fixed to `consent`; purpose must have RequiresDoubleOptIn=true. No route cancels/resends a specific challenge. Starting a new one inserts another row; confirmation exposes no subject identifier in the request for authorization comparison.

### 4.3 Registry bodies expose read/write model fields

Purpose accepts tenant_id, code, category, allowed_channels, requires_affirmative_consent, requires_double_opt_in, active, version, updated_at (`internal/domain/model.go:49-59`). LawfulBasis accepts tenant_id, code, allowed_categories, requires_evidence, active, version, updated_at (`61-69`). PrivacyNotice accepts tenant_id, version, jurisdiction, published_at, active (`71-77`). Tenant and server-managed fields are overwritten/assigned. Service rejects blank purpose category but does not itself enforce an enum; database constraints differ (see F-027/F-028 and the database audit). Registry booleans omit-to-false, so an incomplete replacement POST can deactivate or weaken policy flags. There is no PATCH, ETag/If-Match, expected_version or registry read route to support safe edit forms. This is a full-state last-write-wins contract and must be explicit if retained.

### 4.4 Suppression body

Accepts domain Suppression fields: id, tenant_id, subject_id, scope, purpose, channel, reason, active, version, updated_at (`internal/domain/model.go:107-118`). Service regenerates id and overwrites tenant/update time; repository preserves existing natural-key ID on update. Exact lowercase scope enum only: `global` requires blank purpose/channel; `channel` requires channel and blank purpose; `purpose_channel` requires both (`internal/service/service.go:202-234`). A bool omitted from input means active=false and can clear an existing suppression. No distinction between customer preference and administrator-mandated suppression, no actor-specific clear permission and no expected version exists. Clearing one scope leaves other active scopes in precedence.

### 4.5 Common response shapes

Consent (`internal/domain/model.go:15-39`): always id, tenant_id, subject_id, purpose, channel, legal_basis, status, source, version, created_at, updated_at. Optional scope, jurisdiction, notice_version, receipt_id, granted_at, denied_at, withdrawn_at, expires_at, confirmation_expires_at, confirmed_at. Evidence and confirmation token hash are explicitly omitted from JSON. Pending responses have no receipt; confirmed consent may retain confirmation_expires_at even after token cleared. `status` enum includes expired even though evaluation computes expiry rather than a scheduled status transition.

Decision (`internal/domain/model.go:41-47`): always allowed:boolean, reason:string, evaluated_at:time; consent_id and receipt_id optional. Actual reasons: global_suppression, channel_suppression, purpose_channel_suppression, no_consent, expired, denied, withdrawn, pending_confirmation, policy_unavailable, granted (`internal/service/service.go:353-387`); a stored status `expired` also falls through state reason. The result does not carry tenant, requested subject/purpose/channel, suppression ID/reason, policy version, aggregate version, cache TTL, valid-until or request correlation token. Batch clients must map results by position. Evaluation failure from inactive/missing/error policy is collapsed into normal deny `policy_unavailable`, while suppression/consent repository failure propagates through422.

Receipt (`internal/domain/model.go:85-97`): id, tenant_id, consent_id, subject_id, purpose, channel, notice_version, jurisdiction, evidence:{method,artifact_hash,collected_at}, receipt_hash, issued_at. It does not include notice text/content digest/location, decision status, lawful basis, actor, scope, expiry, accepted purpose/basis policy version or signed proof. F-004/F-005 and the database audit document the proof integrity findings.

## 5. Consent-create idempotency contract

Only API-04 reads the `Idempotency-Key` header (`cmd/server/main.go:196-203`). Key is trimmed and limited to 200 bytes (`internal/service/idempotency.go:40,52`). Its ledger namespace is tenant+key, not route+actor+key. A fingerprint SHA-256 hashes a normalized JSON struct including tenant, **actor**, subject, purpose, channel, legal basis, status, source, scope, expiration, jurisdiction, notice version and Evidence (`internal/service/idempotency.go:17-36,39-68`). Thus replay under a different actor can conflict even if body is identical. Scope map key order is normalized by JSON marshaling, but equivalent timestamp instants with different timezone representations can hash differently. Evidence strings are not normalized. There is no documented expiry/retention or application-specific namespace reservation in README.

The service revalidates live policy **before** consulting the idempotency ledger (`internal/service/idempotency.go:55-58`). A once-successful identical request can later yield 422 when its purpose/basis/notice becomes unavailable. Replay returns the current consent record loaded by ledger ID, not a stored original response snapshot (`internal/store/idempotency.go:33-41,75-83`). After withdrawal, a replay of the original grant body can return 201 with `status=withdrawn`. Neither replay=false/true metadata nor distinct status conveys this. The tests only check same ID/receipt ID for immediate unchanged replay (`cmd/server/idempotency_test.go:52-78`; `internal/service/idempotency_test.go:18-32`). No claim of exactly identical historical response replay is justified.

Required decision: choose and document resource-identity idempotency (return current resource, with clear replay semantics) or response-replay idempotency (return original status/body snapshot). In either choice, define authentication/authorization rechecks, policy revalidation behavior, actor scope, key expiry and HTTP replay metadata. Add tests for replay after withdrawal, policy deactivation, changed actor, key conflict, lost-response retry and concurrent requests. F-017/F-028 and the database audit cover durable ledger integrity and concurrency.

Legacy non-HTTP `Service.Record` emits consent.granted/denied with a different data shape containing legal_basis and without receipt_id/notice_version (`internal/service/service.go:152-178`). No active server handler calls it. Avoid treating that as an active ungoverned public route, but old rows/events or internal code may retain the legacy contract.

Events omit aggregate revision numbers even where the source entity has Version. Registry events omit enough fields that a consumer cannot rebuild the full registry from the event alone; a registry GET route also does not exist. Consent events do not include expiry. Receipt and direct Evaluate API can support some external verification, but complete per-consumer invalidation/recovery/ordering behavior is unverified. F-009/F-010 and the infrastructure audit cover worker ordering and lease guarantees. Required consumer decisions: on-demand decisions vs local caches; revocation/withdrawal propagation deadline; replay/reconciliation; schema compatibility; purpose/channel mapping; canonical subject mapping; fail-closed behavior during service failure. Those contracts must not be fabricated as already implemented.

## 8. Business invariants and confirmed counterexamples

### Current user intent must dominate old confirmation capabilities

Current confirmation locks one token row and checks status/expiry. It does not serialize the complete tenant + canonical subject + purpose + channel preference history. A later denial or withdrawal does not invalidate every earlier pending challenge. Confirming one changes its UpdatedAt, so `FindEffective` chooses it as newest. Two isolated memory probes demonstrated permission being restored after later denial and after withdrawal. This is F-001/P0 and blocks [G-001](19_PRODUCTION_GO_LIVE_CHECKLIST.md#g-001); the durable source has the same token-row/latest-UpdatedAt structure, but the audit did not execute the scenario on YSQL. Source: `internal/service/service.go:256-325`; `internal/store/postgres.go:142-143,340-383`.

[T-001](16_DETAILED_IMPLEMENTATION_BACKLOG.md#t-001) must define and implement a transactionally sequenced current preference or generation, bind challenges to it and invalidate superseded capabilities atomically. Adding only a handler-level status check does not solve the subject-purpose-channel ordering problem. Preserve prior receipts and audit evidence in any additive migration.

### Subject authorization and independent DOI proof are separate controls

A valid same-tenant victim token was sufficient for another self-service customer to confirm and receive the victim consent. Independently, a self-service initiator received its own raw token and immediately confirmed without message delivery. Both were reproduced with httptest and memory storage, not a live provider/database. F-002/[T-002](16_DETAILED_IMPLEMENTATION_BACKLOG.md#t-002) addresses object authorization. F-003/[T-003](16_DETAILED_IMPLEMENTATION_BACKLOG.md#t-003) and [D-02](20_OPEN_DECISIONS_AND_EXTERNAL_DEPENDENCIES.md#d-02) address trusted delivery and capability exposure. Fixing one does not establish the other. Source: `cmd/server/main.go:319-362`; `internal/domain/model.go:127-130`.

### Evaluation must honor the approved time and policy semantics

`Evaluate` accepts `at`, but selects the current suppression and latest UpdatedAt consent without a corresponding historical/effective-time query. It checks expiration and notice publication against at but not GrantedAt/CreatedAt. An isolated governed grant evaluated allowed one hour before it existed. Changing a purpose to require affirmative consent or DOI also left incompatible prior grants allowed in two probes, because the evaluator checks active/channel/category/notice rather than every requirement flag. F-006/F-007 and [D-03](20_OPEN_DECISIONS_AND_EXTERNAL_DEPENDENCIES.md#d-03)/[D-04](20_OPEN_DECISIONS_AND_EXTERNAL_DEPENDENCIES.md#d-04) must decide current-only versus historical decisions and explicit grandfathering. These defects must not be hidden by treating every approved old grant as implicitly grandfathered. Source: `internal/service/service.go:342-387`; `internal/store/postgres.go:142-143`.

An additional probe recorded that withdrawing an older consent after a newer grant causes the older withdrawn row to become effective. That probe is an **OBSERVATION / DECISION REQUIRED**, not a failed assertion against an approved opposite rule. It belongs to D-03/F-006. Scope maps and jurisdiction are also not evaluation dimensions: Scope is stored metadata, and the request has only subject/purpose/channel/at. [D-12](20_OPEN_DECISIONS_AND_EXTERNAL_DEPENDENCIES.md#d-12) must define whether any richer decision context is required.

### Receipt presence is not receipt verification

The hash is SHA-256 over marshaled receipt data before storage. Go IssuedAt nanoseconds are changed by the actual pgx timestamptz codec to microsecond precision. The isolated codec probe used the real dependency codec and showed the hash failing after encode/decode. It did not use a live database, so a real YSQL round trip remains an acceptance requirement. Separately, notice and receipt schemas do not bind immutable accepted text/content and full decision provenance. F-004/F-005 require canonical serialization and sufficient evidence; a nonempty receipt_hash test is inadequate. Source: `internal/service/service.go:108-117`; `internal/store/postgres.go:119-122,289-297`; `internal/domain/model.go:71-97`.

### Atomic writes do not establish complete audit history or propagation

Registry and suppression upserts overwrite current values. Audit rows record actor/action/resource identifier/time but not complete prior rules or suppression state; immutable rows cannot reconstruct facts never recorded, F-029. Outbox publication is asynchronous, with no consumer revision/reconciliation contract, F-010. Event delivery is not complete when the HTTP mutation returns. The worker's lease completion/retry is not fenced to the current claim, F-009. Exact database and worker remediation is in the dedicated reports rather than duplicated as a second backlog here.

## 9. Backend reliability, performance and operational boundaries

Repository methods lack request context and use `context.Background` for durable operations. HTTP read/write timeouts therefore do not cancel queued SQL/transaction work. The API pool is fixed at 25 maximum and2 minimum connections per instance (`internal/store/postgres.go:17-25`); the total must be sized with actual replicas and worker pools under [D-08](20_OPEN_DECISIONS_AND_EXTERNAL_DEPENDENCIES.md#d-08). No load result proves a supported request volume, batch throughput or latency objective. F-012/[T-012](16_DETAILED_IMPLEMENTATION_BACKLOG.md#t-012) requires bounded cancellation/transaction budgets and safe retry behavior; do not add unbounded retries around multi-effect mutations.

Batch evaluation makes sequential reads and can observe different database states across items and between policy reads. Its max100 limit is present, but the original tests do not cover0/100/101, a bad item late in the batch, mixed authorized subjects or concurrent policy changes. Define positional correlation, whole-batch failure and snapshot guarantees in the maintained contract under [T-024](16_DETAILED_IMPLEMENTATION_BACKLOG.md#t-024) and the time/policy decisions D-03/D-04. Source: `internal/service/service.go:237-253`; `cmd/server/main.go:293-316`.

Authentication key misses can amplify outbound JWKS work: five unknown key IDs caused five local fetches in the audit, F-014. No rate limiter is provided by the server. A broker account, gateway or ingress must not be assumed to enforce tenant isolation, request limits, CORS or TLS merely because a manifest references it. [F-019](15_PRODUCTION_BLOCKERS_AND_RISK_REGISTER.md#f-019)/F-020 describe missing transport/identity/stream proof; F-021 covers missing request/lag diagnostics. Health and readiness should be separated from real event-consumer progress.

Dependency versions are pinned in `go.mod:3-21`; both containers use the documented toolchain build. The current vulnerability gate identified advisory findings under [F-011](15_PRODUCTION_BLOCKERS_AND_RISK_REGISTER.md#f-011). This API report does not repeat version recommendations or assert every advisory is exploitable: use the scanner evidence and official-source analysis in [10_SECURITY_PRIVACY_AND_ACCESS_CONTROL_AUDIT.md](10_SECURITY_PRIVACY_AND_ACCESS_CONTROL_AUDIT.md). No compliance certification follows from this review.
