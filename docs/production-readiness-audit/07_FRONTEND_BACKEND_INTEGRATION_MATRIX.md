## 5. Contract mismatches and unconnected boundaries

**No frontend payload mismatch can be proven without the client source.** The audit can instead identify contracts the frontend would have to satisfy and places where the backend cannot currently support a complete interaction. These include the missing read/projection owner, distinction between `sub` and `customer_subject_id`, exact role strings, positional batch results, generic error classification and time-dependent idempotency replay. Sources: `cmd/server/main.go:23-57,109-118,293-316`; `internal/auth/auth.go:27-31,135`; `internal/service/idempotency.go:55-81`.

**A saved preference and a delivered event are different milestones.** Mutation success follows the local transaction. The worker later claims and publishes an event, and there is no real consumer acknowledgement in the HTTP response. Consumers must implement the approved failure/recovery/latency contract; a UI cannot prove all products have stopped communication merely by receiving201. Sources: `internal/store/postgres.go:238-259`; `cmd/outbox-worker/main.go:46-134`.

**Publication metadata is not a complete state projection.** Events have schema_version but no preference revision. Registry payloads omit important rule fields; aggregate_type defaults to consent; expiration is computed on reads without an automatic expiry event. An external projection needs enough information or a supported re-read to recover. F-010 and T-024 must be resolved together before a consumer promises a correct local cached decision.

**Browser and provider boundaries are not configured by a token type alone.** The server has no CORS/OPTIONS middleware or browser session layer. A same-origin gateway may be appropriate, but no implementation is shown. DOI initiation does not accept a verified destination and no dispatch adapter exists. Real origin/session/delivery ownership belongs to D-02/D-10 and the selected consumer contract, not an assumed external service.

## 6. Definition of a complete selected integration

For each approved INT record, the incoming engineer must collect a reviewable evidence bundle through T-023. It must identify the owning application/source revision, configured endpoint and identity roles, canonical subject mapping, purpose/channel and relevant notice/policy mapping, API/event contract version, and data assertions proving the observed result persisted.

The execution must start with the real user or application action and end with its actual business outcome: initial state or saved preference after reload; verified channel confirmation; or a disallowed action prevented at the correct enforcement boundary. Include invalid/expired/missing token, wrong subject/tenant, no consent, denial, withdrawal, suppression, expiry, policy change, timeout/service failure and replay/restart cases relevant to that consumer. For event-based consumers, include reversed order, duplicate event IDs, retry beyond broker deduplication and reconciliation after reconnect. D-08/D-13 must supply measurable propagation and recovery criteria before a timing test can be labeled PASS.

[G-023](19_PRODUCTION_GO_LIVE_CHECKLIST.md#g-023) closes only when every **selected launch** integration has this evidence and a responsible owner. [G-024](19_PRODUCTION_GO_LIVE_CHECKLIST.md#g-024) closes when initial reads and HTTP contracts are explicit and tested. [G-030](19_PRODUCTION_GO_LIVE_CHECKLIST.md#g-030) closes when the actual identity mappings agree with the approved permissions. A source-traced arrow, a nonempty receipt hash, a successful Docker build or a passing memory test cannot substitute for any of those outcomes.
