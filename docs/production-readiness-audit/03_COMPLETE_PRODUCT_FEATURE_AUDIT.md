## Product reconstruction and status vocabulary

NVUTO Consent is a shared backend for privacy, purpose/channel preferences and lawful-basis decisions. Its business value is a consistent permission decision and a durable explanation of that decision across NVUTO products. That is an architectural objective derived from README.md:3-11, not a documented revenue model or market-size claim. Intended customer/tenant scale, regions, commercial model and full UX specifications remain UNKNOWN.

This inventory contains **34 capability records across8 engineering modules**. It includes runtime functionality, persistence, consumer-facing contracts and the operational capabilities necessary to substantiate the README's production claims. This is a coverage inventory, not a completion percentage. Each capability points to its source-backed requirement and concrete gap IDs.

| Status | Meaning |

| PARTIAL | A useful path exists but a required behavior, contract, edge case or proof is incomplete. |

## What is confirmed to work within the executed boundary

The original corpus verifies examples of explicit authentication failure/dev-mode gates, JWT expiry/algorithm/JWKS checks, canonical-subject restriction for evaluate, governed Memory grant and policy validation, no-consent/expiry/withdrawal examples, suppression scope examples, small batch evaluation, single-use DOI on one pending row, optional create idempotency and CloudEvent envelope formatting. Both entry points compile. These are meaningful service slices. Report14 lists every test and its exact outcome.

The SQL implementation uses transactions for governed state/receipt/audit/outbox writes, parameterized tenant queries, cryptographic DOI tokens and immutable evidence triggers. Those source controls are present; target YSQL transaction concurrency, durable receipt verification and broker delivery were not executed here. Distinguish these controls from the unexecuted integration tests that would validate them.

## Critical cross-feature failures

The most consequential defect crosses FT-005 denial, FT-006 withdrawal, FT-011 challenge initiation, FT-012 confirmation and FT-009 evaluation: an old pending row can be confirmed after later negative intent, become newest by updated_at and return allowed=true. Fixing one HTTP handler without a preference-level revision/invalidation design would leave the state invariant exposed. T-001 is therefore a shared prerequisite for the time/policy/event work.

FT-017 authorization and FT-012 confirmation are inconsistent. Most subject-sensitive handlers enforce customer_subject_id for self-service, but confirmation does not. A valid other-customer token is required for the demonstrated same-tenant bypass; the probe does not show token guessing or cross-tenant SQL access. Separately, FT-011 returns the capability to the same untrusted caller, so an own-subject check alone would not restore independent channel proof. T-002 and T-003 solve different problems.

FT-003 notices, FT-013 receipts and FT-014 audit history are related but distinct. Immutable version metadata does not prove the content accepted; a nonempty SHA-256 field does not prove stable receipt verification; immutable audit rows do not reconstruct omitted policy/suppression history. T-004, T-005 and T-029 must establish canonical serialization, full provenance and controlled historical reconstruction without rewriting old evidence.

FT-022 events and FT-023 delivery have two separate contracts: reliable publication and correct consumer state. Fixing stale worker lease ownership does not make out-of-order grant events harmless. Consumers need authoritative evaluation or revision/reconciliation behavior and expiry/policy-change rules. T-009, T-010, T-020 and T-023 cover these dependencies.

## Missing work without invented scope

The supplied implementation does not contain exact notice content binding, a maintained OpenAPI/event contract, an independent DOI delivery connection, complete historical policy/suppression reconstruction, service progress metrics/alerts or a tested target recovery runbook. These are concrete gaps against evidence/governance/integration/production claims. They have executable tickets.

There is no frontend app, screen or UI client in this archive. The8 consumer products are names, not audited applications. Current-preference and registry reads may belong in this service or an external projection; D-01/D-07 and T-024 settle that architecture. No new login, account recovery, billing system or general dashboard is part of the inferred scope.
